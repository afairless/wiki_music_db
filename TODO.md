## Step details

### Step 1 — `feat(cli): add global --verbose and --quiet flags to control log level`

**Rationale:** Users need runtime control over log verbosity without editing config
files. The existing `log_level` field in `wiki_db.toml` provides config-file control,
but CLI flags `--verbose` / `--quiet` offer immediate, per-invocation control with
the expected CLI convention: `--verbose` lowers the filter to `debug`, `--quiet`
raises it to `warn`/`error`.

**Deliverables:**

- `src/cli/mod.rs`:
  - Add to `Cli` struct:

    ```rust
    /// Increase log verbosity (sets RUST_LOG=debug).
    #[arg(long, short, global = true, default_value_t = false)]
    pub verbose: bool,

    /// Decrease log verbosity (sets RUST_LOG=warn).
    #[arg(long, short = 'q', global = true, default_value_t = false)]
    pub quiet: bool,
    ```

  - **Constraint:** `--verbose` and `--quiet` are mutually exclusive. Validate
    at the clap level with `#[arg(conflicts_with = "quiet")]` on `verbose` and
    vice versa (or use `clap::ArgGroup`). A direct `conflicts_with` attribute
    on each is the simplest approach.

- `src/main.rs`:
  - After CLI parsing, resolve the effective log level:

    ```
    CLI --verbose  → debug
    CLI --quiet    → warn
    RUST_LOG env   → env value (highest precedence)
    config file    → config value (used only if no CLI flag and no env var)
    default        → info
    ```

  - Apply the resolved level to the `EnvFilter`.

- Unit tests:
  - `--verbose` flag parsed correctly
  - `--quiet` flag parsed correctly
  - `--verbose --quiet` together → clap parse error (conflicts_with)
  - Default (neither flag) → `false` for both
  - Log level resolution priority: CLI > env > config > default

**Note:** The `--quiet` flag on the `download` subcommand is distinct from this
global flag. Keep both; the download `--quiet` suppresses download-script output
specifically, while the global `--quiet` controls the application's tracing
subscriber level. No renaming or removal needed.

### Step 2 — `chore(dist): add shell completion generation via clap_complete`

**Rationale:** Shell completions improve the user experience. `clap_complete`
integrates directly with the existing `clap` derive setup, requiring minimal code.

**Deliverables:**

- `Cargo.toml`:
  - Add `clap_complete = { version = "4", optional = true }` to dependencies
  - A good default is to keep it non-optional (small dep) since the binary size
    impact is negligible. Mark it optional only if compile time is a concern.

- `src/cli/mod.rs` or `src/main.rs`:
  - Add a `Completion` subcommand (or a hidden CLI feature) that generates
    shell completion scripts:

    ```rust
    use clap_complete::{Generator, Shell, generate_to};

    /// Generate shell completion scripts.
    #[derive(Parser, Debug)]
    pub struct CompletionArgs {
        /// Shell to generate completions for.
        #[arg(value_enum)]
        pub shell: Shell,
        /// Output directory for completion scripts.
        #[arg(long, short, default_value = ".")]
        pub output: PathBuf,
    }
    ```

  - In `main.rs`, handle the `Completion` command:

    ```rust
    Command::Completion(args) => {
        let mut cmd = Cli::command();
        let path = generate_to(
            args.shell,
            &mut cmd,
            "wiki_db",
            &args.output,
        )?;
        println!("Completion script generated: {}", path.display());
        Ok(())
    }
    ```

- README update (or defer to Step 4):
  - Add a note in the README documenting how to generate and install
    completions (e.g., `cargo run -- completion bash`).

- Unit tests:
  - `Completion` subcommand parses shell argument correctly
  - `--output` flag defaults to current directory

### Step 3 — `chore(ci): add GitHub Actions CI pipeline`

**Rationale:** Automated CI ensures code quality on every push. The pipeline runs
the same checks the project already documents: `cargo test`, `cargo clippy`,
`cargo fmt --check`, and `cargo audit`.

**Deliverables:**

- `.github/workflows/ci.yml`:
  - Trigger on `push` to `main`/`master` and on `pull_request`
  - Job: `build-and-test`
    - OS: `ubuntu-latest`
    - Rust toolchain: `stable` with `clippy` and `rustfmt` components
    - Steps:
      1. Checkout repository
      2. Cache cargo registry and build artifacts (using
         `Swatinem/rust-cache` or manual `actions/cache`)
      3. `cargo fmt --check`
      4. `cargo clippy -- -D warnings`
      5. `cargo test`
      6. `cargo audit` (install `cargo-audit` first, or skip if unavailable;
         can be a separate job or step)
    - (Optional) A second job for `cargo build --release` to verify release
      builds succeed, with artifact upload
  - Use `actions-rs/audit-check` or `cargo audit` directly for the audit step.
    Note: `cargo audit` requires `cargo install cargo-audit`. Prefer the
    `cargo audit` GitHub Action (`actions-rs/audit-check`) if available, or
    install manually via `cargo install cargo-audit`.
